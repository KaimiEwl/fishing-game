# Player Progress Standard

## Canonical Store

Player progress lives on the owned Hook & Loot server in SQLite.

- `players` is the canonical player profile table.
- `players.inventory`, `players.cooked_dishes`, and `players.game_progress` hold the active gameplay state that the client reads back from the server.
- Side tables are event or operation tables, not competing progress stores:
  - `player_fishing_casts`
  - `player_cube_rolls`
  - `player_mon_rewards`
  - `mon_withdraw_requests`
  - `premium_fishing_sessions`
  - `premium_fishing_casts`
  - `social_task_verifications`
  - `player_audit_logs`
  - `guest_wallet_links`

## Server Contract

The admin API exposes one canonical read shape: `progress_profile`.

`progress_profile` is generated by `server/player-progress-profile.mjs` and groups raw storage into stable sections:

- `identity`
- `economy`
- `progression`
- `rods`
- `inventory`
- `cooking`
- `tasks`
- `cube`
- `collectionBook`
- `fishingNet`
- `premiumSession`
- `mon`
- `raw`

Game code can keep using the current player payloads during rollout, but new admin/debug work should prefer `progress_profile` over reading random raw fields.

## Admin Edits

Admin edits go through `admin.update_player`, which normalizes and clamps known player fields before writing to SQLite.

Editable advanced JSON sections:

- `inventory`
- `cooked_dishes`
- `game_progress`

The server normalizes those sections again before saving, and writes an `admin_player_updated` audit entry with the edited field list.

## Migration Rule

Do not introduce another primary player-progress store. New gameplay systems should either:

1. write their authoritative player state into `players` through a server action, or
2. create a side table for pending operations / ledgers, then reflect the final player state back into `players`.

The frontend should not author economy, inventory, XP, task, cube, or catch results directly.
